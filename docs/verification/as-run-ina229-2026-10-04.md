# INA229 bench as-run record 2026-10-04

This record assesses the first runs of the [INA229 bench](../tests/ina229.md) on
hardware: TC-13, TC-14 and TC-16 with the INA229 "ina_det" (0.27 Ω shunt) on Pmod J1.
TC-15 (accuracy against reference instruments) was not run and is left for a later
record.

The first run failed TC-14 from step 11. In SPI mode 1, the bench default until then,
some register writes are silently lost: reads and the identity soaks pass, so TC-13
could not show it. The bench now runs the INA229 in mode 3, in which every write
arrived, and TC-13 has a write step (step 3). See
[Lost writes in SPI mode 1](#lost-writes-in-spi-mode-1). TC-16 found that after a supply
interruption the library reports wrong readings as valid until it is reinitialized
([Findings for the libraries](#findings-for-the-libraries)).

## Lost writes in SPI mode 1

Run 1 failed TC-14.11: `SET_ALERT_CONFIG` reported VERIFY_ERROR because DIAG_ALRT read
back unchanged. fprime-ina229 then marks the device uninitialized, as designed, so steps
12 to 14 failed with INVALID_STATE (and `ina timing` counted 8127512 immediate
failures). The diagnostics (`2026-10-04-ina229-det-diagnostics`) narrowed it down:

1. After initialization, every write to ADC_CONFIG was lost: STOP, CONFIGURE_ADC with
   five configurations, at 558 kHz and 1.116 MHz, with the ADC running or shut down, and
   whatever transfer came before (logs 05 to 08, 12, 13). DIAG_ALRT writes were lost too
   (03, 07). CONFIG (through RESET_ACCUMULATORS) and the six limit registers were written
   (04, 08, 09, 11), but SOVL once lost a second write (10).
2. With a raw write command, `ina wreg`, ADC_CONFIG kept 0x0000, 0x0001 and 0xfb6a but
   never 0x0b6a or 0xfb6b, and DIAG_ALRT lost 0x8001 0.1 to 3 ms after a reset but kept
   it at 0 and from 5 ms (14, 15). Nothing else changed when a write was lost.
3. During a write frame the INA229 clocks out the register's previous value. In every
   lost frame those bytes were corrupted (`f800` or `0000` instead of `fb6a`), from the
   first data bit at which MOSI goes high; in every kept frame they were intact (15).
4. The second INA229's chip select was floating. Pulling it up changed nothing (17;
   after the operator restored the disturbed wiring, 16).
5. In mode 2 the same writes were lost and in mode 0 reads failed as well. In mode 3
   every write was kept and every write frame intact, at 558 kHz, 1.116 and 8.93 MHz
   (18). Run 2 then passed with every INA229 point in mode 3.

The cause is not established. Either the INA229 samples on the other edge from the
one its timing diagram was read to show (the bench assumed mode 1 from data sheet
SLYS023A 6.7), or the `cdns,spi` driver puts different edges on the wire from the mode
it is given. fprime-ina229's FT232H notes report a similar CPHA=1 problem with that
host. A logic-analyzer capture of `ina wreg 0x01 0x0b6a` in modes 1 and 3 would decide
it, and is also the open waveform part of INA-HIL-001. The ADXL355, in mode 0, wrote
its registers without a problem in its runs of 2026-09-29 and 2026-10-02.

Changes made because of it, in the same commit as this record:

- `APP_SPI_MODE` defaults to 3; `sensor_bench.py` runs every INA229 point in mode 3.
- TC-13 step 3: raw writes at every SCLK with a check of the write frame, because the
  identity and the soaks only read. It also records the mode 1 result as INFO.
- `ina wreg` in the bench shell, and a [known issue](../known-issues.md).
- `ina stream start <period> <rows>` now ends after `rows` rows when reads fail too
  (in run 1 it went on printing INVALID_STATE rows until `ina stream stop`).
- `sensor_bench.py --interactive TC-15` / `TC-16` runs one operator test case.

## Findings for the libraries

| # | Library | Item | Finding |
|---|---|---|---|
| 1 | fprime-ina229 | INA-HIL-001; `docs/ft232h.md`, `docs/verification.md` | On the TE0715 (`cdns,spi`) the INA229 works only in SPI mode 3: in modes 1 and 2 reads pass but writes are lost depending on the data, in mode 0 reads fail. The library's verified writes caught it (VERIFY_ERROR) and nothing invalid was reported. The library's documentation should say that a host's SPI mode must be checked with writes, not only reads, and name mode 3 as working here. Readback on a real INA229 is shown; the waveform part stays open |
| 2 | fprime-ina229 | TE-INA-004, INA-HIL-005, TC-16 step 4 | After a supply interruption, without reinitialization, the manager reported every reading OK with all seven channels valid, but the current (and with it the power) 10 % low and the energy and charge restarted from zero. The bench documentation assumed SHUNT_CAL would be 0 and the current therefore 0; it is not. The library cannot tell a reset device from a configured one, so a supply glitch gives plausible wrong data. Proposed: detect the reset in `read()`, for example by checking ADC_CONFIG or SHUNT_CAL against the configured values (one more transfer per read) or by watching for ENERGY going backwards, and report it (not valid, `Initialized` = 0) until reinitialized. A register dump after a supply interruption would show the reset values |
| 3 | fprime-ina229 | INA-HIL-004 | The DIAG_ALRT read-modify-write keeps MEMSTAT on silicon (TC-14.11, DIAG_ALRT 0x0003 → 0x8003) |
| 4 | fprime-ina229 | INA-HIL-006 | Manager read at 1.116 MHz: 344 µs mean, 360 µs max (run 2, CPU as after an SD boot) |
